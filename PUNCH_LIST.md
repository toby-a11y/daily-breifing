# The Punch List artifact — spec

A per-day interactive checklist built from the morning briefing, for working
through it live instead of just reading it. Not yet auto-generated by the
scheduled routine (see `ROUTINE.md`) — built and republished by hand in a
working session, currently at:

https://claude.ai/code/artifact/8f773d70-1369-4e9b-85c9-c1e8b070c653

(one URL, reused/republished each session rather than a new artifact per
day — check what's already there before assuming it needs rebuilding from
scratch).

## Item schema

Each item in `state.items` is:

| field | type | meaning |
|---|---|---|
| `id` | string | stable slug, e.g. `heather-parker`. Matches `item_id` in `decisions/*.jsonl` session lines. |
| `group` | string | one of `kari`, `quotes`, `calls`, `ops` — which section it renders under |
| `kind` | string | one of `quote`, `call`, `decision`, `ops`, `watch` — drives the colored chip label |
| `title` | string | rendered as raw HTML (not escaped) — deliberate, so `&amp;` etc. work; never put untrusted text here |
| `detail` | string | escaped on render; the explanatory line under the title |
| `meta` | string | escaped, monospace; short facts (amount, phone number) — omit key if empty |
| `status` | string | `open` \| `doing` \| `done` — see below |
| `note` | string | free text, viewer-editable |
| `links` | array of `{label, url}` | see **Live links** below |

## Interactive check-offs / status

Three states, not a plain checkbox: `open` (red) → `doing` (amber) → `done`
(green, strikethrough + dimmed card). Clicking a status button sets that
state; clicking the already-active one resets to `open`. No fourth
"skipped/won't do" state exists yet — if that's ever needed, add it rather
than repurposing one of the three.

**How changes persist:** the page declares the `artifact` runtime
capability and calls `artifact.publish(...)` on every status/note change
(notes debounced 500ms after the field loses focus), rebuilding the *entire*
document from the in-memory `state` object — never by serializing the live
DOM. Every viewer's open tab reloads to whatever was last published, so two
people editing at once means the second publish wins; there's no merge at
the runtime level. When editing from a session (like this one) rather than
the browser, the safe order is: `Artifact action:"read"` the current live
version first, apply changes on top of *that* JSON (not a stale copy from
earlier in the conversation), then republish — otherwise a publish gets
rejected as a conflict, or worse, silently clobbers what someone did in the
browser in between.

## HubSpot resolving process

Not re-specified here — see `decisions/SCHEMA.md`, section "Standing rule:
check deal activity, not deal stage." Applies to every customer-facing item
on this list, and to the daily automated briefing per `ROUTINE.md`. Short
version: find the deal, then check its associated EMAIL/CALL/MEETING
engagements sorted newest-first — never trust `dealstage` alone, and say so
explicitly when no deal exists at all.

## Live links

Rendered as small pill-shaped `↗ label` buttons under an item's meta line,
`target="_blank"`. Three URL families in use so far, all constructed the
same way a human would navigate there — no shortcuts or guessed formats:

- **Gmail thread**: `https://mail.google.com/mail/u/0/#all/<message_id_or_thread_id>`
  — same formula the Open Loops board itself uses for its own links, and
  the one `decisions/SCHEMA.md` documents for deriving a link from a
  `decisionlog_email` line's `message_id`.
- **HubSpot deal record**: `https://app.hubspot.com/contacts/43586414/record/0-3/<deal_id>`
- **HubSpot email engagement**: the `urlTemplate` HubSpot's own
  `search_crm_objects` result returns for `EMAIL` objects — filters the
  CRM UI down to that one engagement by `hs_object_id`. Don't hand-build
  this one; copy the `urlTemplate` from the actual tool result and
  substitute the id, since its query-param shape isn't a simple format
  string.

An item with no traceable source (an internal ask, a HubSpot-logged call
with no email) gets an empty `links: []` rather than an omitted field or a
placeholder link — the schema always has the key.

## Daily carry-forward (as of the routine wiring it in — see `ROUTINE.md`)

Now built by the scheduled routine each morning, on top of whatever's
already live — never a from-scratch rebuild. The merge, in order:

1. **Read** the current live artifact first (`Artifact action:"read"`).
   No prior version (first run ever) means start from an empty item list.
2. **Drop** every item whose `status` is `done`. Done means resolved —
   it doesn't need to keep occupying the list. (Its history isn't lost:
   the day it was marked done, that change already went into
   `decisions/*.jsonl` as a `source:"session"` line if it happened in a
   working session, or is simply reflected in that day's board snapshot.)
3. **Keep**, unchanged, every remaining item (`open` or `doing`) whose
   `id` still corresponds to something live on the board or in today's
   briefing — same `status`, same `note`, untouched. Don't regenerate
   its `detail`/`meta`/`links` from scratch either unless the underlying
   fact actually changed; a viewer's in-progress note is the whole point
   of carrying it forward.
4. **Add** new items for anything in today's briefing (important emails,
   messages requiring response, action items, Kari's projects) that
   doesn't already have a matching `id`. Run the HubSpot resolving
   process and populate `links` for these the same as any other session
   would.
5. **Reconcile stale ones**: an item still `open`/`doing` whose
   underlying board entry has moved to `archived` or vanished should be
   updated (detail note that it resolved elsewhere) or dropped — use
   judgment, don't leave a zombie item nobody will ever click.

**Stable `id` convention** (needed for step 3 to match anything):
`kebab-case`, built from the customer/system name plus enough of the
ask to disambiguate — `heather-parker`, `roger-gural`, `zapier-errors` —
never date-based, never a counter. The same underlying task must produce
the same `id` on every run, or carry-forward silently breaks and every
day looks like a fresh list.

## Failure mode

If the artifact read or publish fails, the routine says so in the
briefing's output in one line and moves on — the four files in `ROUTINE.md`
are the routine's actual deliverable; the punch list is additive and
shouldn't block them.
